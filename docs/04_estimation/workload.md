# 工数見積もり

## 見積もりの方法

**ストーリーポイント法** で見積もる。

- 1ポイント = 1時間（目安）
- ポイントは 1・2・3・5・8・13 から選ぶ（相対見積もり）
- 13ポイント以上になる作業は、分割する

| ポイント | 目安 |
|---------|------|
| 1 | 非常に簡単（既知の作業） |
| 2 | 簡単 |
| 3 | 普通 |
| 5 | やや複雑 |
| 8 | 複雑 |
| 13 | 非常に複雑（分割する） |

**前提**
- ブログアプリ（Week 1〜17）で作った Docker・Breeze・GitHub Actions の構成を流用できるため、環境構築は小さめに見積もる
- 開発者は1人

## 時間が足りないときの対策

フェーズ1は、バッファを入れると使える時間より 5時間多い。遅れが出たら、次の順で後回しにする。

1. **写真アップロード（No.10）をフェーズ2へ回す**（−3時間）：写真は任意の項目のため、なくても募集はできる
2. **テスト（No.12）を、Policy と「行きたい！」だけにする**（−1〜2時間）
3. それでも間に合わないときは、「行きたい！」の Ajax をやめて、通常のフォーム送信（ページの再読み込みあり）にする（−2時間）。提出後に Ajax にする

## リスク

| リスク | 対策 |
|--------|------|
| 大学の授業・課題で、予定どおりに時間が取れない | 毎日の終わりに [schedule.md](schedule.md) と実績を比べ、遅れたら上の「対策」を早めに使う |
| 初めて作る機能（年齢の計算、相互フォローの判定）に時間がかかる | フェーズ2 の Could に入れているため、最初の提出には影響しない |
| 本番環境（AWS）の再開でトラブルが起きる | デプロイはフェーズ2 にして、最初の提出はローカル（Docker）で動く状態にする |
