# 工数見積もり

## 見積もりの方法

**ストーリーポイント法** で見積もる。

- 1ポイント = 1時間（目安）
- ポイントは 1・2・3・5・8・13 から選ぶ（相対見積もり）
- 13ポイント以上になる作業は、分割する

| ポイント | 目安 |
|---------|------|
| 1 | 非常に簡単（既知の作業） |
| 2 | 簡単 |
| 3 | 普通 |
| 5 | やや複雑 |
| 8 | 複雑 |
| 13 | 非常に複雑（分割する） |

**前提**
- ブログアプリ（Week 1〜17）で作った Docker・Breeze・GitHub Actions の構成を流用できるため、環境構築は小さめに見積もる
- 開発者は1人

## 使える時間

| 期間 | 内容 | 時間 |
|------|------|------|
| 11/28（土）〜11/30（月） | 前倒しで環境構築・DB を作る（休日 6時間 × 2日 ＋ 平日 3時間 × 1日） | 15時間 |
| 12/1（火）〜12/9（水） | 実装（平日 3時間 × 7日 ＋ 休日 6時間 × 2日） | 33時間 |

## 時間が足りないときの対策

フェーズ1は、バッファを入れると使える時間より 7時間多い。遅れが出たら、次の順で後回しにする（[sprint-plan.md](../sprint-plan.md) の「遅れたときの対策」と同じ）。

**必須の機能（ログイン・CRUD・Policy・キーワード検索・写真アップロード・「行きたい！」の Ajax）は削らない。**

1. **テスト（No.12）を、Policy と「行きたい！」だけにする**（−1〜2時間）
2. **共通レイアウト（No.6）を Breeze のレイアウトのまま使う**（−1〜2時間）：見た目の調整は提出後に回す
3. **「日時が過ぎた募集を一覧に出さない」処理（No.7 の一部）を提出後に回す**（−1時間）
4. それでも間に合わないときは、必須の機能は削らずに、講師に相談する

- Week 20 の初版では「写真アップロードを後回し」「Ajax をやめる」としていたが、どちらも教材の必須の機能のため、Week 21 で変えた

## リスク

| リスク | 対策 |
|--------|------|
| 大学の授業・課題で、予定どおりに時間が取れない | 毎日の終わりに [schedule.md](schedule.md) と実績を比べ、遅れたら上の「対策」を早めに使う |
| 初めて作る機能（年齢の計算、相互フォローの判定）に時間がかかる | フェーズ2 の Could に入れているため、最初の提出には影響しない |
| 本番環境（AWS）の再開でトラブルが起きる | デプロイはフェーズ2 にして、最初の提出はローカル（Docker）で動く状態にする |
