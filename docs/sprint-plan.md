# スプリント計画

oshi-tomo の実装（Week 22〜24）を、スクラムのスプリントに分けて計画する。

- 工数の根拠は [04_estimation/workload.md](04_estimation/workload.md) を参照
- 進捗は GitHub Projects のボードで管理する（ボードの URL は PR に書く）
- この計画は初版。Week 21 で見直して確定する

## 1. 前提

| 項目 | 内容 |
|------|------|
| 見積もりの単位 | ストーリーポイント（1ポイント ＝ 1時間の目安） |
| 開発者 | 1人（プロダクトオーナー・スクラムマスター・開発チームを1人で兼ねる） |
| 使える時間 | 平日 3時間・休日 6時間。最初の提出（12/9）までに **48時間** |
| 最初の提出 | **12/9（水）** |

### スプリントの区切り方（教材との違い）

教材では「Week 22〜24 の3スプリント、各1週間」としているが、この計画では **自分のスケジュールの Week に合わせて区切る**。そのため、スプリントの長さはそろっていない。

| 週 | 期間 |
|----|------|
| Week 22 | 12/1〜12/4 |
| Week 23 | 12/5〜12/8 |
| Week 24 | 12/9 |

また、11/28〜11/30 に前倒しで行う環境構築は、3つのスプリントの外に **スプリント0（準備）** として置く。

### 隙間時間の扱い

11/25〜11/27 の隙間時間は、日によって取れるかどうか分からないため、**計画の時間（48時間）には入れない**。

- 隙間時間は、まず Week 21（期限 11/27）の作業に使う
- 余った分でスプリント0 の作業（環境構築）を先に進め、その分を後のスプリントの余裕にする

## 2. ユーザーストーリーの優先順位（プロダクトバックログ）

ユーザーストーリーは [requirements.md](requirements.md) の US-01〜US-22。

### 並べ方の考え方

1. **ほかの機能の前提になるものを先に作る**：会員登録がないと、募集の投稿も「行きたい！」もできない
2. **アプリの中心を先に作る**：oshi-tomo の中心は「募集して、『行きたい！』で一緒に行く仲間が見つかる」こと。ここまで動けば、アプリとして最低限使える
3. **同じ Must でも、なくても中心が使えるものは後にする**：検索（F-05）は募集が少ないうちはなくても探せる。プロフィール（F-02）がなくても、募集と「行きたい！」はできる。どちらも最初の提出の後に作る
4. **時間が足りないときに外しやすいものは後ろに置く**：写真（US-05）は任意の項目のため、スプリント2 の中で「行きたい！」の前に置き、遅れたときに外しやすくする

## 3. スプリントの全体像

| スプリント | 期間 | 使える時間 | 作業 | 余裕 | スプリントゴール |
|-----------|------|-----------|------|------|-----------------|
| 0（準備） | 11/28〜11/30 | 15h | 15pt | 0h | Docker で動き、18歳以上の人が会員登録できる |
| 1（Week 22） | 12/1〜12/4 | 12h | 12pt | 0h | 募集の一覧・詳細が見られ、募集を投稿できる |

**余裕をスプリント2 に集めた理由**：スプリント2 には、初めて作る Ajax（「行きたい！」）があり、一番つまずきやすい。そのため、会員登録をスプリント0 に、募集の作成をスプリント1 に前倒しして、スプリント2 に 4時間の余裕を作った。

## 5. 完了の定義

すべてのスプリントで共通。次の3つを満たしたら、その作業は「完了」とする。

- 画面で動作を確かめた
- テスト（`php artisan test`）と CI（GitHub Actions）が通っている
- PR を作って main にマージした（GitHub Projects のカードが Done になる）

## 6. スクラムのイベント（1人で行う形）

| イベント | 1人で行うときのやり方 |
|---------|---------------------|
| スプリントプランニング | この計画を作ること。各スプリントの初日に、前のスプリントの結果を見て内容を見直す |
| デイリースクラム | 毎日の作業の終わりに、上の日別の表と実際に終わった作業を比べる。困っていることがあれば講師に相談する |
| スプリントレビュー | 各スプリントの最終日に、スプリントゴールの状態になっているか画面で確かめる |
| スプリントレトロスペクティブ | Week 24 で行う（まだ実行していないスプリントは振り返れないため） |

## 7. 遅れたときの対策

まずはスプリント2 の予備 4時間で吸収する。それでも間に合わないときだけ、次の順で後回しにする（[workload.md](04_estimation/workload.md) の「時間が足りないときの対策」と同じ）。

1. 写真アップロード（No.10）を提出後に回す（−3時間）
2. テスト（No.12）を、Policy と「行きたい！」だけにする（−1〜2時間）
3. 「行きたい！」の Ajax をやめて、通常のフォーム送信にする（−2時間）。提出後に Ajax にする

## 8. 提出後（12/10〜）

最初の提出のフィードバックを反映しながら、優先順位の表の 7 番から順に進める。

1. Must の残り：検索・絞り込み（F-05）→ プロフィール（F-02）→ 本番環境へのデプロイ
2. Should：「行きたい！」を押した人の一覧（F-08）→ 推しの登録（F-09）→ 投稿（F-10）
3. Could：年齢の範囲表示（F-14）→ フォロー（F-15）→ 通報（F-11）→ 公式情報（F-12）→ お問い合わせ（F-13）
